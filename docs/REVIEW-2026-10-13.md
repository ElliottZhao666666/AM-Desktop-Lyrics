运行主链路为：Windows SMTC → Rust 媒体状态/进度 → 歌词 provider → 统一 LyricsDocument → Tauri 事件 → Vue 单调时钟插值 → 逐行/逐词显示。数据层主要是 JSON 文件：设置外层 Base64、普通歌词缓存、永久自定义池和 AMLL-DB 文件缓存；没有数据库或独立后台服务代码。

有价值的基础设计包括：严格选择 Apple Music 会话而不控制其他播放器；耗时 SMTC 主循环独立线程；旧歌词请求 generation 校验；前端即时清空切歌歌词；歌词偏移带 revision；窗口关闭隐藏复用；日志、手动纠错和永久匹配齐备。当前欠缺主要发生在这些模块的边界。

**问题清单**

P1 表示优先修复，会丢配置、串词或阻断核心链路；P2 表示常见功能错误或条件性可靠性问题。以下区分“隔离复现”“代码确认”和“待实机确认”，不把静态风险包装成已观察到的用户故障。

**01 · P1 · 保存通用/外观设置或窗口位置会丢失渠道配置与 Token（隔离复现）**

位置：`src-tauri/src/lib.rs:71`、`:142`、`:566`；`src-tauri/src/config.rs:94`。

`config::write_config` 把 `config` 嵌入同一 `settings.json`，而 `AppSettings` 没有这个字段。`write_settings_unlocked` 序列化 AppSettings 后直接覆盖文件。因此保存渠道和 Token 后，再点击通用/外观“应用”，或启用位置记忆后拖动/缩放窗口，都会删除 `config`。隔离运行原始写入函数后，合成 Token 丢失，原本关闭的 QQ 被默认重新开启。

建议统一持久化根模型，或拆分配置文件，并在窗口位置写入时只更新对应字段。文件写入应有原子替换，避免半写入。

**02 · P1 · SMTC 时间轴把旧位置当作当前权威时间，歌词可能周期性回退（隔离复现机制，实机频率待确认）**

位置：`src-tauri/src/media/smtc.rs:486`；`src/App.vue:154`。

每秒读 Position 后直接发送，没有处理 LastUpdatedTime、播放速率或相同时间轴快照。Microsoft 定义 Position 是 LastUpdatedTime 时刻的位置，并不保证每次轮询已自动前进。当播放器返回重复快照时，前端先插值到 11000ms，下一次相同 10000ms 快照又触发超过 300ms 的回跳。此机制用实际前端函数复现。

建议以时间轴更新时间为基准，结合播放状态/速率估算当前值，区分“相同快照”和真实 seek；监听时间轴变化，保留周期校验。[Microsoft 时间轴语义](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties?view=winrt-26100)。

**03 · P1 · API 仅按歌曲时长选择缓存 ID，可能永久缓存错误歌词（隔离复现）**

位置：`src-tauri/src/lyrics/cache_scanner.rs:10`、`:29`；`provider.rs:129`。

匹配条件只有 body dur 与当前时长差 ≤ 4000ms，没有歌名、歌手、专辑、请求时间或真实歌曲 ID 交叉验证。隔离缓存里放入另一首 180 秒歌曲，它直接被识别为目标 ID。随后 API 返回文档的 track 被替换为当前歌曲，并进入普通缓存，前端无法发现身份错配。

建议先确认可靠歌曲身份，再请求歌词；不能把“时长相近”当作确定匹配。

**04 · P1 · 切歌检索可能使用上一首的时长（代码确认）**

位置：`src-tauri/src/media/smtc.rs:126`、`:381`、`:486`；`provider.rs:28`。

只有首次连接时先读时长；后续媒体属性事件延迟 400ms 后从全局 CURRENT_MEDIA_POSITION 取时长，这个值由独立每秒轮询更新。新歌事件落在轮询之间就可能拿到旧歌时长，进一步触发 03。之后正确时长到达没有重新检索，因为 LAST_REQUESTED_TRACK 去重直接返回。

建议在同一次新歌处理里读取元数据和时间轴，并绑定歌曲/会话版本；未知时长应允许稍后补查。

**05 · P1 · 启动期间丢失歌词事件后无法从快照恢复（代码确认）**

位置：`src-tauri/src/lib.rs:591` 附近；`media/smtc.rs:592`；`src/App.vue:207`；`provider.rs:28`。

SMTC 在 setup 时启动，永久池/自身缓存命中可以很快发出歌词。若发生在前端监听注册前，启动快照只能补回 media 和 position，没有歌词文档/加载状态；provider 对同一 track 不重复获取，界面可能一直“正在搜索歌词”。

建议后端保存当前歌词及状态，统一快照含歌曲版本、媒体、进度、歌词、加载状态；或前端监听就绪后请求可重复的当前歌词恢复。

**06 · P1 · QQ 未找到可靠匹配时仍选第一项（代码确认）**

位置：`src-tauri/src/lyrics/qq_music.rs:35`。

精确候选不存在时 `.or_else(|| candidates.first())` 无条件使用搜索第一项。没有专辑/版本/时长约束，多歌手和 Live 等变体还容易使严格标题匹配失败，错误结果随后按当前 track 持久化。候选没有歌词时也不继续尝试其他候选。

建议增加匹配评分和最低置信度，无可靠匹配返回 NotFound；区分 Live、Remix 等版本，允许尝试多个可信候选。

**07 · P1 · Apple Music 缓存扫描只认时间新鲜度，无法确认内容属于当前曲目（代码确认）**

位置：`src-tauri/src/lyrics/cache.rs:122`、`:161`、`:185`。

直接给最新可解析 TTML 套上请求 track，2 秒时间容差不能防止快速切歌时读到前一首响应。反方向，启动时已播放较久或点击“重新扫描”，真实目标缓存如果早于请求超过 2 秒则全部被跳过。缺少身份确认同时导致错配和漏配。

建议与 03 一起设计统一缓存匹配策略，明确“切歌抓新响应”和“按身份重新读取既有缓存”的区别。

**08 · P2 · 手动重取/应用发生错误后加载状态不收尾（代码确认）**

位置：`src-tauri/src/lyrics/provider.rs:179`、`:214`、`:240`、`:265`、`:286`。

begin_forced_request 先发 Loading，后续网络、任务、歌词不存在或文件保存错误通过 `?` 返回，没有给主歌词窗口发 Error/恢复状态。设置页会弹错误，主窗口却继续显示“正在搜索歌词”。LyricsLoadState::Error 和前端错误显示存在，但当前 provider 没有实际发出 Error 的路径。

建议所有请求出口统一终态；失败可保留此前可用歌词，并清除失败请求去重状态。

**09 · P2 · API 没有总超时，且同步扫描占用异步运行线程（代码及文档确认）**

位置：`src-tauri/src/lyrics/am_api.rs:25`；`provider.rs:129`；`cache_scanner.rs:10`。

API HTTP 客户端未设置 connect/total timeout；渠道顺序执行，默认 API 优先，服务连接或响应卡住时不能及时进入缓存/QQ 回退。reqwest 0.12.28 默认无总超时。缓存 ID 扫描还直接在 async 任务内执行递归文件读取和最多 7 次 240ms thread::sleep；generation 只丢结果，没有取消这些工作。

建议设置超时预算，把扫描放入 spawn_blocking，切歌取消/停止旧请求，缺 Token 时及时跳过 API。[reqwest 0.12.28 超时说明](https://docs.rs/reqwest/0.12.28/reqwest/struct.ClientBuilder.html#method.timeout)。

**10 · P2 · 缓存 TTML 解析丢英文空格，无时间容器吞掉子词时间（隔离复现）**

位置：`src-tauri/src/lyrics/ttml.rs:39`、`:135`；`src/components/LyricsBoard.vue:12`。

`<span>Hello</span> <span>world</span>` 的中间空格写入 line.text，但前端有 words 时只渲染 words，最终是 Helloworld。无时间外层 span 被默认赋予整行时间，所有子 span 合并为一个词；相同输入旧解析器得到 1 词，API 解析器得到 2 词。

建议统一两套解析器，保留正文全部字符及词间空白，容器与有时间词元分开处理。

**11 · P2 · API 逐行歌词缺失 end 后旧行持续累积（隔离复现）**

位置：`src-tauri/src/lyrics/ttml_parser.rs:96`；`src/components/LyricsBoard.vue:56`。

API 解析器对无词时间/无 end 的行不按下一行或 body duration 推断结束。前端把 end=null 看作永不结束，最多保留最后三行。输入 1s 的 first 和 4s 的 second，在 5s 时仍同时显示两行；缓存解析器对此会推断 first.end=4000。间奏判断也会把 begin 当作缺失的 end，存在提前进入间奏的问题。

建议统一行结束推断规则，保留有明确时间的真实重叠，避免把未知 end 等同无限活动。

**12 · P2 · 有时间 span 与普通文本混排时丢字（隔离复现）**

位置：`src-tauri/src/lyrics/ttml_parser.rs:113`；`src/components/LyricsBoard.vue:12`。

输入 `PREFIX <span ...>word</span> SUFFIX`，完整 line.text 是 PREFIX word SUFFIX，words 仅有 word；前端选择 words 模式后前后文本消失。英文空白处理的修复没有覆盖普通文本节点。

建议明确 mixed-content 模型，把无时间文本保留为布局片段，或在无法完整表达时回退整行显示。

**13 · P2 · 主题编辑器不恢复已保存/导入的编辑状态，改单项会覆盖整套主题（隔离复现）**

位置：`src/components/SettingsView.vue:211`、`:261`、`:352`、`:389` 附近。

只加载 themeCss，editor 始终来自 DEFAULT_EDITOR；导入文件和手改 CSS 也没有同步 editor。下次启动显示已保存 CSS 预览，但控件仍是默认值，修改字号等单项就用默认 editor 生成整套 CSS，覆盖此前字体、颜色、效果。selectedPreset 还可能错误显示默认。

建议主题文件和设置持久化结构化 editor；对于任意 CSS 明确源码编辑模式，避免无声重建覆盖。

**14 · P2 · 自定义字体输入第一个字符后输入框消失（隔离复现）**

位置：`src/components/SettingsView.vue:34`、`:35`、`:353`。

输入框显示条件是 editor.fontFamily==='custom'，@input 却立即把该字段替换为用户输入，比如“霞”，条件变 false，无法连续输入完整字体名。

建议把字体选择模式和实际字体字符串分开保存。

**15 · P2 · 把汉字“一”无条件当元数据分隔符（代码确认）**

位置：`src-tauri/src/media/smtc.rs:166`、`:188`。

metadata_segments 同时按破折号和“一”拆分。合法歌手“李一桐”会变成歌手“李”，并可能生成专辑“桐”；包含多个“一”的正常歌曲标题也可能被解释成 title/artist/album。真实 AlbumTitle 存在也不能避免歌手被截断。

建议只有结构化格式可信或与已知 album 后缀吻合时清洗，避免把常用汉字全局当标点。

**16 · P2 · 默认 API Token 初始化路径不一致（隔离复现）**

位置：`src-tauri/src/config.rs:15`、`:18`、`:53`。

AmApiTokens derive(Default) 生成空字符串；serde(default=default_auth_token) 仅在反序列化缺少字段时调用。新安装/旧配置没有 config 时 AppConfig::default 仍取到空 Token，源码的默认 Token 常量并不会发挥预期作用。隔离结果：Default 是空，反序列化 `{}` 是非空。

建议明确采用用户 Token 或可更新的公共授权获取流程，统一默认行为及有效期提示。报告不复述源码中的 Token 字符串。

**17 · P2 · 歌词渠道“保存并生效”不会刷新当前曲目，手动开关语义不一致（代码确认）**

位置：`src-tauri/src/lib.rs:198`；`provider.rs:28`、`:48`、`:247`、`:358`；`src/components/SettingsView.vue:424`。

save_config 只落盘，没有配置变更事件或当前曲目重新检索；LAST_REQUESTED_TRACK 又阻止同曲目重试。关闭 manual 只阻止普通 apply_manual，永久池读取和 apply_custom 没有该检查。普通手动匹配文档的 source 仍为 qqMusic，关闭 QQ 后它又会被自身缓存过滤掉。自动/手动/永久来源的开关和优先级没有一致模型。

建议区分自动 QQ、临时手动、永久绑定，定义明确开关语义；配置改变时取消并重新检索当前曲目。

**18 · P2 · 前端曲目身份忽略 album，旧任务也缺少会话版本（代码确认，快速切歌待实机验证）**

位置：`src/App.vue:187`、`:247` 附近、`:291` 附近；`src-tauri/src/media/smtc.rs:381`。

后端 TrackIdentity 比较含 album，前端切歌判断和歌词事件筛选只有 title/artist。同名同歌手不同专辑/版本不能可靠隔离。新增 400ms 延迟任务还没有当前 session/generation 校验，注销事件并不会取消已派发任务，旧会话的迟到读取可能重新覆盖新状态。

**补充可靠性和维护问题**

- 播放控制是同步 Tauri command，并在主线程 `.get()` 等待 WinRT，Apple Music 无响应时存在 UI 卡住风险。改为 async/专门线程并限制等待。[Tauri 命令线程说明](https://v2.tauri.app/develop/calling-rust/#async-commands)。
- 普通缓存、永久池和设置直接覆盖文件，无事务或损坏恢复；永久池以歌名/歌手为键，故意忽略专辑，跨版本绑定是当前设计限制。
- 降低缓存数上限仅在下一次 local_cache_put 才截断；切换繁简设置不使已转换的普通缓存失效。API 的 autoChs 与通用的 OpenCC 开关还是两套独立状态，界面没有统一控制。
- 歌词行超过最终 end 仍回退显示最后一行；歌词过长/大字号/三条重叠行没有可靠空间适配。没有实现歌词滚动或换行动画，仅有播放状态整体透明度/缩放过渡。
- 默认 Rust CSS 没有前端生成 CSS 的 stack width 规则，两处默认主题也不是同一份（渐变颜色数量不同）；应使用单一默认来源。
- 日志按启动保留 current/previous，但单次运行文件不限制大小、没有时间戳，read_current_log 全量读取；每个移动/缩放事件都创建一个睡眠线程作防抖，长时间操作可能产生大量短命线程。
- 没有单实例保护；多个进程会共享设置、缓存和日志，启动日志轮转可能因为文件占用失败。需实机验证双开路径。
- 设置“取消”和标题栏关闭只是 hide，保留未保存的编辑状态；歌词偏移更已实时应用。应明确取消是否回滚以及再次打开是否重新载入。
- 系统字体只枚举 HKLM，未覆盖 HKCU 用户安装字体，也未从注册表显示名拆分字体家族；不是字体文件加载器。
- Token 帮助链接 `/help/get-token` 在本仓库静态官网中没有对应页面。线上可能有其他部署，不能仅据此判定线上 404。
- README 的 clone 命令含 Markdown 链接语法，不能直接执行；下载/特性请求链接是 `#`，mailto 使用 `mailto://`；绿色版没有专门发布步骤。Rust 1.70+ 声明不符合 `Option::is_none_or` 的 Rust 1.82 起支持情况，实际依赖最低版本还应另行锁定。[Rust Option 文档](https://doc.rust-lang.org/std/option/enum.Option.html#method.is_none_or)。
- 全部窗口共用宽权限且 CSP=null；主题 CSS 可作用于整个页面。后续接入外部内容时应重新审视能力边界。当前审查没有证据表明已存在远程代码执行漏洞。
- 官网为静态展示，不包含更新服务代码。即使 Git 历史写着“完善更新服务后端”，本仓库也无法据此确认线上部署、Release 发布、公钥匹配和真实升级链路。

**建议的开发顺序与验收标准**

1. **配置和状态恢复先稳定。** 修复 01、05、08、16、17，统一配置根模型和当前状态快照。验收：渠道/Token 保存后应用主题、拖动窗口、重启都保留；启动缓存命中稳定显示；断网/错误都有明确终态；当前曲目配置变更可以重试。
2. **统一歌曲身份与时间基准。** 修复 02、03、04、06、07、15、18、20。验收：相近时长不同歌曲、同名 Live/Studio、多歌手、快速 A→B→A、暂停/seek/Apple Music 重启，都不串词、不回跳、不污染缓存。
3. **合并解析器并补样本回归。** 修复 10、11、12、19，再完善逐词和双行。验收：英文空白、中文音节、无时间容器、混合文本、重叠演唱、缺 end、LRC 多标签/offset 都得到可预期模型。
4. **补主题和桌面交互闭环。** 修复 13、14、21、22，确定取消语义和字体模式。验收：保存/重启/导入后控件与预览一致，改单项不覆盖其他项；150%/200% DPI 和错位双屏可用。
